## 一、教师端的目标定位（依据现有文档）

综合功能文档与评审反馈（Jon），教师端要解决的核心诉求是两件事：**数据分析 + 布题**，并有四条设计约束：

1. **班级级别**呈现数据，不指向任何个人（隐私边界）；
2. **不只是描述性统计**：给出结论式洞察（Insights）+ 可自然语言追问的助手；
3. **图表简化**，只放能指导教学决策的少量图；
4. 教师基于数据洞察**直接布置练习**，形成"看数据 → 定教学动作"的闭环。

对应实现：`frontend/teacher_app.py`（独立应用，8502 端口）+ `backend/analytics.py`（日志聚合与洞察）+ `backend/assignments.py`（布题存储）。

### 文档层面已承认的功能缺口（教师文档 §10"后续可扩展"）

- 无时间趋势图（班级掌握度曲线、gaming 随时间变化）；
- **布题与学生端未打通**：学生看不到布置的任务；
- 无多班级分组、无导出 CSV；
- 洞察助手未接 RAG。

### 文档层面的逻辑不完善之处

| # | 问题 | 说明 |
|---|---|---|
| W1 | **布题闭环只写了一半** | 文档把"布题"列为教师两大核心诉求之一，但布置的任务学生端不读取、学生练习结果也不回流（`/grade` 无埋点），所以教师布题后**永远看不到任何效果数据**。文档只在"后续可扩展"轻描淡写带过，实际上这是核心诉求未闭环，应升级为高优先级。 |
| W2 | **latency_ms 的语义错误已被指出但教师端仍在使用** | `reference/Next_Steps_Plan.md` §4.2 明确写了"`latency_ms` 是 LLM 响应时间，不能当 time-on-task"，但教师端 gaming 判定（`analytics.py`）恰恰用 `latency_ms < 1500` 判定学生"赶答"。两份文档结论互相矛盾，实现采信了错误的一方。 |
| W3 | **解题率的口径未定义清楚** | 文档说"解题率 = 会话中最终解出的比例"，但没说明：只统计 tutor 会话（is_solved 由 LLM 判定），不含学生练习判分（/grade）结果。教师直觉理解的"解题率"（做题正确率）与实际口径完全不同，容易误读。 |
| W4 | **实验核心（explain vs control）在教师端缺位** | 整个项目的研究主线是 explain-to-unlock 对照实验，但教师端没有任何两组对比视图，只能跑离线脚本 `scripts/analyze_logs.py`。文档没有解释为什么教师/研究者看不到这组最重要的数据。 |
| W5 | **模拟数据与真实数据的边界只靠口头约定** | 文档说"正式统计时删除 `sim_*.jsonl` 即可"，但 `analytics.py` 不区分 sim 前缀、界面无任何"含模拟数据"标识，靠人工记得删文件，必然出事故。 |
| W6 | **语言状态描述自相矛盾** | 学生文档 §0.2 说"语言状态跨页面（学生页/教师页）一致"，教师文档 §0 说"两个界面语言状态各自独立"。实现是后者（两个独立 Streamlit 应用不共享 session state）。 |

## 二、教师端各模块数据需求清单

> 图例：✅ 数据真实可得 ｜ ⚠️ 数据可得但口径有问题 ｜ ❌ 数据缺口（前端想要/应该要，后端给不了）

### 2.1 顶部 KPI（8 项）

| 指标 | 需要的数据 | 来源 | 状态 |
|---|---|---|---|
| 活跃学生 `n_students` | 会话的去重 student_id | `session_start` 事件 | ⚠️ 学生不填名字全部记为 `anon`，合并成 1 人（实测 12 会话只算出 4 人） |
| 会话数 `n_sessions` | 有 turn 的会话数 | `turn` 事件 | ⚠️ 学生页一进入就自动建自由会话，含大量"打开即走"的噪声会话 |
| 解题率 `solve_rate` | 每会话 is_solved | `turn.is_solved`（LLM 判定） | ⚠️ 不含练习判分结果（见 ❌ 练习事件） |
| 平均推理 `avg_reasoning` | 每回合 assessment | `turn.reasoning_assessment` | ⚠️ 未过滤"无需解释"的回合，none=0 全部计入，系统性低估（实测 87.5% 回合为 none，均值仅 0.32/4） |
| 平均掌握度 `avg_final_mastery` | 每会话 mastery 峰值 | `turn.mastery` | ✅（但 mastery 本身是启发式 +10/+25，未校准） |
| 平均轮数 `avg_turns_per_session` | 每会话 turn 数 | `turn` 事件 | ✅ |
| gaming 率 `gaming_rate` | 护栏命中、回合耗时、解释词数 | `turn.action / latency_ms / student_text` | ❌ **缺学生端计时**：`latency_ms` 是 LLM 响应耗时，"赶答"判定对真实数据无效 |
| 护栏拦截率 `guardrail_rate` | action == blocked 的回合占比 | `turn.action` | ✅ |

### 2.2 知识点图表（左栏）

| 需要的数据 | 来源 | 状态 |
|---|---|---|
| 每会话所属知识点 | `session_start.topic`（仅模拟数据有）或 `problem_id → topic` 映射 | ❌ **断链**：映射表只覆盖 `data/problems.json` 的 12 道种子题；学生从"生成题目"链接助教的会话（problem_id 为生成 id）映射失败，全部落进 "General / Free chat"（实测 12 会话有 6 个落入该桶） |
| 每知识点 attempts / 解题率 / 推理 / 掌握 / gaming | 上述 turn 聚合 | ⚠️ 继承上面所有口径问题 |
| （应有）时间维度 | 事件均带 `ts`，但接口未暴露 | ❌ 无按周/按月筛选，无趋势 |

### 2.3 推理质量分布图

| 需要的数据 | 来源 | 状态 |
|---|---|---|
| 各等级回合占比 | `turn.reasoning_assessment` | ⚠️ 同 2.1：应只统计"助教要求解释后的回合"（`asks_for_explanation` 字段日志里有，未使用） |

### 2.4 洞察卡片（Insights）

| 需要的数据 | 来源 | 状态 |
|---|---|---|
| ClassAnalytics 全量聚合 | `analytics.build_insights` 规则生成 | ⚠️ 未排除 "General / Free chat" 桶——自由聊天被当成"最薄弱知识点"输出误导性洞察（实测已出现）；文案英文写死，无中文 |

### 2.5 自然语言助手（Ask about your class）

| 需要的数据 | 来源 | 状态 |
|---|---|---|
| 班级事实块（facts block） | `analytics._facts_block` → LLM | ✅ 有降级兜底 |
| （应有）多轮对话上下文 | 无 | ❌ 单轮问答，不能追问 |
| （应有）时间序列/条件对比事实 | 无 | ❌ 助手只知道全时段聚合数，答不了"这周比上周如何""explain 组效果如何" |

### 2.6 布题（Assign practice）

| 需要的数据 | 来源 | 状态 |
|---|---|---|
| 任务 CRUD | `data/assignments.json` | ✅ |
| （应有）学生端展示任务 | 学生端不读 `/assignments` | ❌ **闭环断裂**：布置的任务学生永远看不到 |
| （应有）任务完成度/正确率回流 | `/grade` 不写日志，日志里无 assignment_id | ❌ 教师看不到任何布题效果 |
| （应有）任务对应的题目实体 | 无：任务只存 `n_questions` 数字，不生成/绑定真实题目 | ❌ "布置 5 道题"实际上没有 5 道题存在 |
| （应有）截止时间/班级分组 | 无字段 | ❌（文档已列为后续） |

### 2.7 缺失的关键埋点事件（后端全局）

当前日志只有 `session_start` 和 `turn` 两种事件。教师端要成立，至少需要补：

| 事件 | 关键字段 | 支撑的教师端功能 |
|---|---|---|
| `question_generated` | qid, type, topic, difficulty | 出题量、题型分布、（未来）验证通过率 |
| `answer_submitted` | qid, topic, correct, time_to_answer_ms, attempt_no, assignment_id? | **真实做题正确率**（按知识点/按任务），布题效果回流 |
| `session_start` 增加 `topic` | problem.topic（数据现成，见 store.py） | 修复知识点归因断链 |
| 客户端计时字段 | client_think_ms（前端计时后随消息上报） | 让 gaming / time-on-task 指标成立 |

## 三、现状页面评审

### 3.1 逻辑错误（优先级：高）

| # | 问题 | 位置 | 证据与影响 | 建议 |
|---|---|---|---|---|
| L1 | **知识点归因断链** | `backend/store.py` `create_session`（不记 topic）；`backend/analytics.py` `_problem_topic_map`（只覆盖种子题库） | 生成题会话的 problem_id 不在种子题库中，topic 回退为 "General / Free chat"。实测线上数据 12 会话中 6 个落入该桶，按知识点图表基本失真 | `session_start` 事件写入 `problem.topic`（一行改动，数据现成）；旧日志兼容回退 |
| L2 | **误导性洞察："最薄弱知识点 = 自由聊天"** | `analytics.build_insights` | weakest 排序未排除 "General / Free chat"。实测已输出该洞察，教学上无意义且丢脸 | 排除 free chat 桶后再排序 |
| L3 | **推理质量被系统性低估** | `analytics.compute`：所有 turn 的 assessment 计入均值/分布 | 学生说"好的/继续"、助教主动给提示的回合 assessment=none 按 0 分计入。实测 87.5% 回合为 none、均值 0.32/4，并连锁触发"全班推理质量低"警告——统计口径伪影，不是学生真实水平 | 只统计"上一轮助教 `asks_for_explanation=True`"的回合，或把 none 从分母剔除、单列"未解释占比" |
| L4 | **gaming 判定用错时间量** | `analytics.py` `_FAST_TURN_MS`；`backend/main.py` `send_message`（latency 计的是 process_turn 耗时） | `latency_ms` 是 LLM 响应时间（真实值 2s+），`<1500ms` 的"赶答"判定对真实数据几乎永不触发，只对模拟数据有效。`Next_Steps_Plan.md` §4.2 早已指出 | 前端记录"看到回复 → 提交下一条"的 client_think_ms 随请求上报；判定改用该字段 |
| L5 | **练习数据完全不进日志，布题闭环两处断裂** | `backend/main.py` `/grade`（无埋点）；学生端不读 `/assignments` | 学生做题的对错、耗时、题型全部丢失；教师布置的任务学生看不到、效果无从谈起。"数据分析 + 布题"两大核心诉求，布题这半个实际是摆设 | 补 `answer_submitted` 埋点；学生端侧边栏/路径条展示任务列表；任务带 assignment_id 串起数据 |
| L6 | **模拟数据静默混入统计** | `analytics._load_events`（glob 所有 `*.jsonl`） | 跑过 `seed_demo_logs.py` 后教师看到掺假数据，界面无任何提示；忘删 `sim_*` 会污染正式结论 | analytics 识别 `sim_` 前缀：默认剔除 + 接口加 `include_sim` 参数供演示；界面显示"含 N 条模拟会话"徽标 |
| L7 | **匿名学生合并计数** | `store.create_session`（默认 `anon`） | 实测 12 会话 `n_students=4`，其中大量是同一个 "anon"。活跃学生数不可信 | 前端生成并持久化匿名设备 id（如 `anon_<hash>`）；或 KPI 标注"仅统计具名学生" |
| L8 | **实验条件对比缺位** | 整个教师端 | explain vs control 是项目研究主线，教师端一个数字都看不到 | KPI 或图表区增加两组对比（解题率/推理/轮数），数据日志里现成 |
| L9 | **无效会话稀释指标** | `analytics.compute` | 学生页进入即自动建自由会话；1 轮寒暄的会话与完整辅导会话等权重平均，拉低 solve_rate / mastery | 设最小有效轮数（如 ≥2 轮）或区分"练习会话/自由会话"两套指标 |

### 3.2 设计缺陷（优先级：中）

| # | 问题 | 位置 | 说明与建议 |
|---|---|---|---|
| D1 | **任何交互都触发全页重算，页面迟钝的直接根源** | `teacher_app.py` 顶部 `fetch_class_analytics()`（无缓存）+ Streamlit 全页 rerun 模型 | 切语言、输入问题、点删除，都会重新请求 `/analytics/class`，后端再全量重读所有 jsonl。建议：`st.cache_data(ttl=30)` 包住 analytics 请求 + 后端按日志文件 mtime 缓存聚合结果 + 用 `@st.fragment` 把问答/布题区隔离成局部刷新 |
| D2 | **图表弱且顺序错误** | `st.bar_chart`（3 处） | 无 tooltip、无排序控制；推理分布 x 轴被按字母序排列（adequate→none→partial→strong→weak），破坏 none→strong 的语义顺序；知识点图按字母序而非学习路径顺序。建议换 Altair（Streamlit 原生支持），显式指定轴序 |
| D3 | **无时间维度** | 全页 | 所有 KPI 都是"有史以来"总量，无本周/上月筛选、无趋势线。事件都带 `ts`，是接口没暴露。教学决策需要"变化"而不只是"存量" |
| D4 | **洞察与助手回答英文写死** | `analytics.build_insights` / `answer_question` | 中文界面下右栏整块是英文。洞察应做成结构化数据（kind + 参数）由前端 i18n 渲染；LLM 回答按当前语言指定输出语言 |
| D5 | **问答助手单轮、旧答案残留** | `teacher_app.py` `insight_answer` | 不能追问；换问题后旧答案仍挂着。建议改成小型对话流（history 列表），至少提交新问题时清空旧答案 |
| D6 | **洞察与布题不联动** | 右栏 → 布题区 | 洞察说"Chain Rule 最薄弱"，教师还要手动在下拉框找 Chain Rule。应在洞察卡片上放"就此布题"按钮，预填知识点/难度 |
| D7 | **无任何访问控制** | `teacher_app.py` / 后端 analytics、assignments 路由 | 知道端口就能看全班数据、增删任务。demo 可接受，但文档大谈隐私边界时应至少加个共享口令（如 env 里配 `TEACHER_TOKEN`） |
| D8 | **8 个 KPI 平铺无主次** | KPI 区 | 解题率、薄弱知识点等决策指标与 gaming/护栏等低频指标视觉等权。建议 4 个主 KPI + 次要指标收进"更多"或与洞察合并 |

### 3.3 页面瑕疵（优先级：低）

| # | 问题 | 位置 | 说明 |
|---|---|---|---|
| Q1 | 洞察卡片严重度色条从未生效 | `teacher_app.py` `SEVERITY_CLASS`（定义后未使用）；`ui.py` `.insight-info/-warning/-critical` | CSS 写了、字典建了，但 Streamlit 容器没挂上类名，卡片只剩 emoji 区分。死代码 + 设计意图未实现 |
| Q2 | "任务已创建"提示一闪即逝 | `teacher_app.py` 布题提交后 `st.success` 紧跟 `st.rerun()` | rerun 立即清屏，成功反馈基本看不到。应改 `st.toast` 或把 flag 存 session_state 在 rerun 后展示 |
| Q3 | 百分比截断不是四舍五入 | KPI 区 `int(rate*100)` | 58.9% 显示 58%。用 `round()` |
| Q4 | 语言状态双应用不同步 | `ui.language_toggle`（两个独立 app 各自的 session state） | 与学生文档"跨页面一致"的说法矛盾（见 W6） |
| Q5 | 模拟数据用了非法 action 值 | `scripts/seed_demo_logs.py`（`action: "solved"`） | schema 的 TutorTurn action 枚举里没有 `solved`；真实/模拟数据结构不一致，未来加校验会炸 |
| Q6 | 知识点名称永远是英文 | 图表/表格/洞察 | i18n 只翻了 UI 框架文案，7 个 topic 名（Limits、Chain Rule…）在中文界面下保持英文 |
| Q7 | `main.py` 顶部 docstring 过期 | `backend/main.py` | 只列了 5 个 endpoint，实际有 13 个；文档腐化 |
| Q8 | 刷新按钮语义弱 | 侧边栏 `st.rerun()` | 与任何交互都触发的 rerun 无区别；若 D1 加了缓存，此按钮应改为"清缓存 + 重取" |

## 四、技术架构评估：要不要换底层框架？

### 4.1 先说结论

| 层 | 结论 |
|---|---|
| **FastAPI（后端）** | **保留，不换。** 接口划分清晰、Pydantic 契约完整、CORS 已开。教师端的问题（统计口径、埋点缺失、无缓存）全是应用层代码问题，与框架无关。换掉 FastAPI 是零收益的折腾 |
| **Streamlit（教师端前端）** | **是"不灵敏"的真正来源，但先优化、后评估替换。** 理由见下 |

### 4.2 "页面不灵敏"的归因

体验差 = 数据错（第三节 L1–L9，占问题的一半以上）+ 交互慢（D1 全页 rerun + 无缓存）+ 表现力弱（D2 图表、Q1 样式挂不上）。
其中**数据错与框架无关**——不先修数据，换任何前端框架都是把错误的数字渲染得更快更好看。

Streamlit 的框架性天花板（优化也绕不开的部分）：

- 任何控件交互 = 整页脚本重跑，组件级局部更新只有受限的 `@st.fragment`；
- 自定义样式只能靠 CSS hack 注入，选择器随版本变（Q1 就是受害者）；
- 无真正的路由、鉴权、组件生态；多应用只能多端口（学生 8501 / 教师 8502 的别扭由此而来）。

### 4.3 三条路线对比

| 方案 | 内容 | 成本 | 交互体验上限 | 与现有后端兼容 |
|---|---|---|---|---|
| **A. 保留 Streamlit + 性能/图表优化** | `st.cache_data` + 后端聚合缓存 + `@st.fragment` 局部刷新 + Altair 图表 + toast 修复 | **1–2 天** | 中：能消除 70% 卡顿感，但 rerun 模型和样式 hack 仍在 | 无缝 |
| **B. 教师端单独迁移 React**（Vite + ECharts/Recharts，直连 FastAPI） | 学生端不动，只重写教师仪表盘为 SPA | **1–2 周**（含联调） | 高：组件级更新、真 tooltip/联动图表、可加登录 | 后端 API 已就绪、CORS 已开，改动为零 |
| **C. 换 NiceGUI / Gradio / Panel** | 整体换 Python 系 UI 框架 | 3–5 天 | 中低：仍是 Python 服务端渲染思路，定制上限有限 | 需重写两个前端 |

### 4.4 建议的决策路径

1. **第一步（必做，本周）：修数据 + 方案 A。** 先修 L1–L6（其中 L1、L2、L3、L6 都是几行到几十行的改动），再做缓存与 fragment 优化。做完后教师端"数字可信 + 基本流畅"，足以支撑课程评审演示。
2. **第二步（视评审要求）：教师端评估方案 B。** 触发条件：评审明确要求产品级交互（图表联动、下钻、登录），或路线图确定要接 Learnvia（届时反正要 Web 组件化）。届时**只迁教师端**，学生端与 FastAPI 全部不动。
3. **方案 C 不建议**：迁移成本不低而上限提升有限，处在 A 和 B 之间的尴尬位置。
