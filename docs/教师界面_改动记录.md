## 二、页面结构：三段式

页面自上而下回答教师的三个问题，取代原来"KPI 平铺 + 左右两栏"的无主次布局：

```
① 概览 Overview   —— 班级现在怎么样？   4 张主 KPI 卡 + 次级指标条
② 诊断 Diagnose   —— 问题出在哪？       左：知识点健康度 / 推理质量 / 条件对比
                                        右：洞察卡片 / 数据助手 / 练习正确率
③ 行动 Act        —— 接下来做什么？     布题表单 + 任务列表
```

模块约定与 `optimizeStudentPage` 分支的学生端一致：一个区块一个文件、统一
`render_*_panel()` 入口、**面板不发 HTTP**（数据与 API 函数由编排器注入）、
数据契约写在模块头部 docstring。教师端模块放在独立子目录 `frontend/teacher/`，
与学生端平铺模块隔离，避免两分支合并时互相干扰。

## 六、第三轮（同日）：布题模块重新设计为"组卷制"

**动因**：原设计"一个任务 = 单一题型 × 单一难度 × N 道"不符合真实作业形态——
老师布置的练习应当是**混合题组**（热身 → 巩固 → 提高）。

### 6.1 数据模型（唯一一处后端改动）

- `backend/schemas.py`：新增 `AssignmentItem`（topic × qtype × difficulty × count），
  `AssignmentCreate` 改为 `{title, note, items: AssignmentItem[]}`；
- `backend/assignments.py`：读取时自动把旧格式记录升级为题组制（`_upgrade`），
  API 路由不变；
- 此改动仅涉及布题功能自身的 JSON 存储，不属于此前推迟的分析/埋点链路。
  **后端需重启**才能接受新格式。

### 6.2 前端组卷编辑器（`teacher/assign.py` 重写）

| 能力 | 说明 |
|---|---|
| 题组编辑表 | 每行独立选知识点/题型/难度/题数，可加行删行（上限 8 组），跨知识点混合也支持 |
| 一键组卷模板 | **基础巩固**（4 简单单选 + 3 简单填空 + 2 中等单选）、**综合训练**（四种题型中等难度）、**挑战拔高**（困难填空 + 步骤排序为主），悬停有教学法说明 |
| 合计条 | 实时显示"共 N 道题 · 预计 M 分钟"（按题型基准分钟 × 难度系数估算） |
| 智能预填 | 从洞察/知识点图点"布置练习"过来时，自动按基础巩固模板生成该知识点的递进题组，并建议标题「XX」巩固练习 |
| 任务列表 | 显示总题数、预计用时、逐题组明细、完成情况占位 |

### 6.3 验证

- AppTest 端到端：套模板（4 题组）→ 加一组 → 填标题 → 提交 →
  API 确认 items 结构与题数 → 删除清理，全程无异常；
- 新增 `ui.rerun_fragment()`：fragment 内局部刷新，在测试环境（全页运行模式）
  自动回退为整页刷新；
- 修复一次 Windows 编码事故：PowerShell 批量替换把 `assign.py`/`assistant.py`
  的非 ASCII 字符写坏，`assign.py` 已改为纯 ASCII（符号用 Unicode 转义）以绝后患。

## 七、第四轮（同日）：智能模板 + 班级选择器

### 7.1 预填按班级数据自动选模板

从洞察卡片 / 知识点图点"布置练习"时，题组模板不再固定用"基础巩固"，
而是根据**该知识点的班级解题率**自动选择（`assign._pick_template`）：

| 解题率 | 模板 | 理由 |
|---|---|---|
| < 40%（或无数据） | 基础巩固 | 班级明显吃力，从简单题递进 |
| 40% – 70% | 综合训练 | 基础尚可，四种题型均衡练 |
| > 70% | 挑战拔高 | 学得好，直接上高难度 |

预填提示条会注明所选模板及依据（"已按「基础巩固」模板生成题组（根据该知识点的
解题率自动选择）"），教师仍可一键换成其他模板或手动改题组。
`solve_rate` 由知识点图 / 洞察卡随回调传入（`request_assign` 新增参数）。

### 7.2 侧边栏班级选择器（UI 就位，等名单接口）

一个老师可能管多个班级。侧边栏新增**班级**下拉框，按既定的"契约先行"模式实现：

- 前端调 `GET /classes`（`api.fetch_classes`，5 分钟缓存）：接口尚不存在时返回
  None，选择器显示锁定的"全部学生"单项 + 说明文字"接入班级名单后，这里就能切换
  不同班级"——不做"切了也不变"的假开关；
- 接口一旦返回 `[{id, name}]` 列表，同一个选择器自动变为可切换，选中的
  `class_id` 随 `/analytics/class?class_id=` 透传（后端当前忽略该参数，实现
  过滤后数字即按班显示）；
- 后端待办已登记为设计文档 §5 · B9：班级名单、学生-班级映射（session_start 带
  class_id）、analytics 与 assignments 按班过滤。

### 7.3 验证

- AppTest：点击解题率 0% 的知识点按钮 → 预填 `template=foundation`，
  题组为 4 简单单选 + 3 简单填空 + 2 中等单选；
- 阈值单测：`None/0.2 → foundation`，`0.5 → mixed`，`0.9 → challenge`；
- 截图确认：班级选择器以锁定态正常显示于侧边栏（截图已更新）。

## 八、第五轮（同日）：长内容原地滚动，不再撑长页面

**动因**：内容会随数据增长的模块（洞察卡片等）此前直接把页面越撑越长，
应该固定高度、内部出滚动条。

统一处理了三处会无限变长的区域（`st.container(height=...)`）：

| 模块 | 规则 |
|---|---|
| 数据告诉你（洞察卡片） | 超过 3 张卡片时，卡片区固定 380px 内部滚动；3 张以内保持自然高度，不留空白 |
| 问一问班级数据（对话记录） | 有对话时，记录区固定 320px 滚动；建议问题与输入框始终固定可见 |
| 当前任务（任务列表） | 超过 3 条任务时，列表区固定 460px 滚动 |

验证：无头渲染无异常；截图确认洞察区在 4 张卡片时正确收进滚动区、
后续模块位置不再被推移。

## 十、第七轮：导航分区（不再单页堆叠）

**动因**：所有看板堆在一页里，页面很长，布题编辑器被压在最下面。

### 10.1 导航结构（新增 `teacher/nav.py`）

标题下方一排导航按钮，**只渲染选中的分区**（选中项 `ss.nav_section` 存在会话状态里）：

| 导航项 | 内容 | 回答的问题 |
|---|---|---|

## 十一、助手"答非所问"问题：模型服务中断 + 静默兜底

**现象**：不管问什么，助手都回同一句 "Based on the class data, the weakest area is
Derivatives..."。

**根因（两层）**：

1. **模型服务不可用**：`yunwu.ai` 已停止 API 服务，旧域名对每次调用返回
   `403 您的账号已迁移至 api.openlux.ai`。新站需要重新签发 key（旧 key 在新站报
   "无效的令牌"）。
2. **失败被静默吞掉**：`analytics.answer_question` 用 `except Exception` 捕获后
   直接返回规则兜底摘要，界面上完全看不出模型没工作——那句重复的英文正是兜底文案。

**修复**：

| 位置 | 改动 |
|---|---|
| `backend/config.py`、`.env`、`.env.example`、两个 README | 端点改为 `https://api.openlux.ai/v1`，并注明旧站已停用 |
| `backend/analytics.py` | `answer_question` 改为返回 `(answer, llm_available)`，失败时 **记录真实异常**（此前完全无日志） |
| `backend/schemas.py`、`main.py` | `AnalyticsAnswer` 增加 `llm_available` 字段并透传 |
| `frontend/teacher/assistant.py`、`i18n.py` | 兜底回答上方显示醒目提示："AI 模型连不上，下面是按规则自动生成的班级摘要，并不是针对你这个问题的回答" |
| `backend/socratic.py` | 助教回合的 LLM 失败同样是静默兜底，**补上日志**（见下方遗留） |

**验证**（换上新 key 后）：

| 链路 | 结果 |
|---|---|
| `/analytics/ask` × 3 个不同问题 | `llm_available=true`，三次回答各不相同；中文提问用中文回答 |
| `/generate` 出题 | 200，题干与 4 个选项正常 |
| `/session/start` + 发送消息 | 助教正常回复，assessment=strong、action=advance |
| 模型不可用时的降级路径 | 后端记录 401 真实原因，前端显示中文提示（换 key 前已验证） |

> **对既往数据的影响：已核查，本次未发生污染。** 隐患是真实存在的——
> `socratic.process_turn` 在 LLM 失败时返回固定话术
> （"Sorry, I had trouble forming a response"，`reasoning_assessment="none"`），
> 却**仍按正常回合写入日志**，无法与真实回合区分。但扫描全部日志（33 条 turn 事件）
> 后确认该话术出现 **0 次**：停服窗口内没有学生使用助教，日志里存的都是真实模型回复。
>
> 因此教师端 none 占比偏高**不是**由此造成的，而是统计口径问题（分析文档 L3：
> 把"助教没要求解释"的回合也按 0 分计入）。给 `TutorTurn` 增加 `is_fallback`
> 字段仍应尽快落地，避免下次服务中断时静默污染数据——已登记在
> [待办清单](待办_改进清单.md) P0。
