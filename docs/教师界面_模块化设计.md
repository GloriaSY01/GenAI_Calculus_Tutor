# 教师界面 · 模块化设计（Teacher Dashboard v2）

> 目标：把教师端从"一个 194 行的单文件页面"重构为与 `optimizeStudentPage` 分支学生端
> 一致的**模块化面板结构**。本文档定义：页面结构、每个模块放什么、每个模块需要什么数据、
> 模块间如何交互、哪些数据现在就有、哪些依赖后端改动（**后端改动全部往后放**，见 §5）。
>
> 问题编号（L1/D1/Q1…）沿用 `docs/教师界面_分析与改进方案.md`。

---

## 0. 设计依据：对齐学生端分支的模块化约定

`optimizeStudentPage` 分支（`frontend/student-page.md`）确立了四条约定，教师端照搬：

1. **一个界面区块 = 一个模块文件**，入口统一为 `render_xxx_panel(...)`；
2. **模块只做 UI**：数据和回调由编排器（主应用文件）显式传入，模块不直接发 HTTP 请求；
   API 调用函数作为参数注入（如学生端把 `send_message` 传给 `tutor.py`）；
3. **数据契约写在模块头部**：包括未来数据源的占位（学生端 `concept.fetch_concept`
   注明"future: GET /concept?topic=..."），后端没准备好时 UI 先渲染空态；
4. **每个页面配一份设计文档**（本文件即教师端的对应物）。

> ⚠️ 合并提示：`optimizeStudentPage` 与 `yt_branch` **都重写了** `frontend/streamlit_app.py`
> （前者 focus 模式 + 英文模块，后者学习路径 + i18n/ui 主题），两分支合并时该文件必然冲突，
> 需要专门排期处理。因此教师端模块**放进独立子目录 `frontend/teacher/`**，
> 不与学生端模块（`practice.py`、`tutor.py` 等平铺文件）混在一起，保证教师端重构
> 不受学生端合并的影响。

## 1. 页面总体结构

> **导航分区（v3）**：页面不再单页堆叠，标题下方一排导航按钮切换四个分区，
> 每次只渲染选中的那一个（`teacher/nav.py`，状态存 `ss.nav_section`）：
>
> | 导航项 | 模块 |
> |---|---|
> | 📊 总览 | `kpi` + `insights` + `nav.render_guide`（引导卡）+ `condition_compare` |
> | 🎯 学情诊断 | `topic_health` + `reasoning_quality` ｜ `practice_stats` |
> | ✏️ 布置练习 | `assign`（组卷表单 ｜ 任务列表） |
> | 🤖 数据助手 | `assistant` ｜ `insights`（只读参考） |
>
> 下方的三段式描述保留为**推荐阅读顺序**（总览 → 诊断 → 布题），
> 段落眉标仍标注"第一步／第二步／第三步"。

学生端适合"聚焦模式"（一次只看一个阶段），教师端是仪表盘，**不适合**聚焦模式。
采用「**概览 → 诊断 → 行动**」三段纵向结构，回答教师的三个问题：
*班级现在怎么样？→ 问题出在哪？→ 我该做什么？*

```
┌─ Sidebar ────────────┐  ┌─ Header：标题 · 数据状态徽标 · EN/中文 ────────────┐
│  数据范围（时间/班级） │  ├─ ① 概览  kpi_panel                                │
│  含模拟数据开关        │  ├─ ② 诊断  ┌──────────────────┬─────────────────┐  │
│  刷新数据             │  │          │ topic_health      │ insights         │  │
│                      │  │          │ reasoning_quality │ assistant        │  │
│                      │  │          │ condition_compare │                  │  │
│                      │  │          └──────────────────┴─────────────────┘  │
│                      │  ├─ ③ 行动  assign_panel（表单 + 任务列表）           │
└──────────────────────┘  └────────────────────────────────────────────────┘
```

文件结构：

```
frontend/
├── teacher_app.py            # 编排器：布局、状态、API 注入（保持入口不变，8502）
└── teacher/
    ├── __init__.py
    ├── kpi.py                # ① 班级概览 KPI
    ├── topic_health.py       # ② 知识点健康度（图 + 表）
    ├── reasoning_quality.py  # ② 推理质量分布
    ├── condition_compare.py  # ② explain vs control 对比（研究视图）
    ├── insights.py           # ② 洞察卡片
    ├── assistant.py          # ② 班级数据问答助手
    ├── assign.py             # ③ 布题（表单 + 列表）
    └── practice_stats.py     # ②（预留）练习判分正确率，等后端埋点
```

## 2. 模块定义（放什么 + 需要什么数据）

> 数据状态图例：✅ 现有接口即可 ｜ ⚠️ 现有但口径待修（后端往后放，UI 先照现状渲染）
> ｜ ❌ 依赖后端新增（本期只留 UI 空态占位）

### 2.1 `kpi.py` — 班级概览

**职责**：一屏回答"班级现在怎么样"。解决 D8（KPI 平铺无主次）。

**放什么**
- **主 KPI 一行 4 个大卡**：活跃学生、解题率、平均掌握度、会话数；
- **次级指标一行小字/折叠**：平均推理、平均轮数、gaming 率、护栏拦截率（低频指标降级展示）；
- 百分比统一四舍五入（修 Q3）；
- 顶部小徽标：数据里含模拟会话时显示"含 N 条模拟数据"（对应 L6，徽标 UI 先做，
  后端标记字段往后放，字段缺失时不显示）。

**接口**：`render_kpi_panel(data: dict) -> None`（`data` 为 `/analytics/class` 响应）

**需要什么数据**

| 字段 | 来源 | 状态 |
|---|---|---|
| `n_students, n_sessions, solve_rate, avg_final_mastery` | GET /analytics/class | ✅（n_students 受 anon 合并影响 L7，口径后修） |
| `avg_reasoning, avg_turns_per_session, gaming_rate, guardrail_rate` | 同上 | ⚠️ L3/L4 口径问题，后端后修，UI 不变 |
| `n_sim_sessions`（模拟会话数徽标） | 同上（待新增字段） | ❌ 后端往后放 |

### 2.2 `topic_health.py` — 知识点健康度

**职责**：一眼看出"哪个知识点需要补"。解决 D2（图表弱、排序错）。

**放什么**
- 单张**水平条形图**（Altair）：每知识点一行，按解题率**升序**（最差的在最上面），
  条上悬停 tooltip 显示 attempts / 推理 / 掌握 / gaming；
- 图下折叠完整表格（沿用现有 expander）；
- "General / Free chat" 桶**单独放到图外**，以一行说明文字展示（"另有 N 个自由聊天会话"），
  不参与知识点排序（对应 L1/L2 的 UI 侧规避——即使后端归因未修，图表也不再被污染）；
- **只做诊断，不放布题入口**：布题动作统一收在第三步（见 §2.7 快捷组卷）。

**接口**：`render_topic_health_panel(by_topic: list[dict]) -> None`

**需要什么数据**

| 字段 | 来源 | 状态 |
|---|---|---|
| `by_topic[]: topic, attempts, solve_rate, avg_reasoning, avg_final_mastery, gaming_rate` | GET /analytics/class | ✅（生成题会话落入 free chat 的归因断链 L1 后端后修；UI 侧先把该桶剥离） |
| （未来）知识点学习路径顺序作为次级排序 | GET /learning-path | ✅ 现有接口，可直接用 |

### 2.3 `reasoning_quality.py` — 推理质量分布

**职责**：回答"学生是只写步骤，还是真的在解释"。

**放什么**
- 分布条形图（Altair），x 轴**显式指定顺序** none→weak→partial→adequate→strong（修 D2 字母序问题）；
- 图注说明当前口径（"统计所有回合"），后端修 L3 后改为"仅统计被要求解释的回合"，
  文案从 i18n 取，切换口径时只改文案；
- 预留一个小指标位："解释响应率"（被要求解释后真的给出解释的比例）。

**接口**：`render_reasoning_panel(distribution: dict, *, n_explanation_turns: int | None) -> None`

**需要什么数据**

| 字段 | 来源 | 状态 |
|---|---|---|
| `reasoning_distribution: {level: share}` | GET /analytics/class | ⚠️ L3 口径待修，UI 不变 |
| `n_explanation_turns`、解释响应率 | 同上（待新增字段） | ❌ 后端往后放，缺失时隐藏该指标位 |

### 2.4 `condition_compare.py` — explain vs control 对比（研究视图）

**职责**：把项目研究主线（L8）搬进界面：两组的解题率/推理/轮数并排对比。

**放什么**
- 两列小卡（explain / control）：会话数、解题率、平均推理、平均轮数；
- 无数据时整个模块隐藏（不渲染空框）；
- 加一行免责说明：仅供研究观察，教学决策以知识点视图为准。

**接口**：`render_condition_panel(by_condition: list[dict] | None) -> None`

**需要什么数据**

| 字段 | 来源 | 状态 |
|---|---|---|
| `by_condition[]: condition, n_sessions, solve_rate, avg_reasoning, avg_turns` | GET /analytics/class（待新增字段） | ❌ 后端往后放（日志里 condition 现成，聚合是几行代码）；本期 UI 写好、拿不到字段就隐藏 |

### 2.5 `insights.py` — 洞察卡片

**职责**："不只是描述性统计"的落点：结论式发现。**只做诊断**，
布题动作统一收在第三步（§2.7），本模块不放任何操作按钮。

**放什么**
- 卡片列表：severity 色条（用自绘 HTML 卡片实现左侧色条，修 Q1 的类名挂不上问题）
  + 标题 + 详情；洞察文案由前端按 i18n 模板本地生成（双语，见改动记录 §5.3）；
- 超过 3 张卡片时固定高度内部滚动，不撑长页面；
- UI 侧兜底过滤：关于 "General / Free chat" 的 weak_topic 洞察不展示（L2 的 UI 规避，
  后端修复后此过滤自然失效）。

**接口**：`render_insights_panel(data: dict) -> None`

**需要什么数据**

| 字段 | 来源 | 状态 |
|---|---|---|
| `insights[]: kind, severity, title, detail` | GET /analytics/class | ✅（文案英文写死 D4；双语化需要后端改为结构化洞察 kind+params，往后放） |
| （未来）结构化洞察参数 `params: {topic, rate, ...}` 供前端 i18n 渲染 | 同上 | ❌ 后端往后放 |

### 2.6 `assistant.py` — 班级数据问答助手

**职责**：自然语言追问班级数据。解决 D5（单轮、旧答案残留）。

**放什么**
- 小型**对话流**（本地 history 列表，`st.chat_message` 气泡），不再是"一问一答一个 info 框"；
- 示例问题做成 3 个**可点击 chip 按钮**（对齐学生端 suggested prompts 的交互习惯），
  点击即发送，不再经过 selectbox + 手动点提问两步；
- 提交新问题时清空输入框、追加到 history；
- 整个模块包在 `@st.fragment` 里，提问不触发全页 rerun（D1 的前端侧缓解）。

**接口**：`render_assistant_panel(ss, *, ask_fn) -> None`（`ask_fn = api.ask_analytics` 注入）

**需要什么数据**

| 字段 | 来源 | 状态 |
|---|---|---|
| `answer` | POST /analytics/ask | ✅（多轮上下文、按界面语言回答，后端往后放；本期 history 只存在前端，每次仍发单问题） |

### 2.7 `assign.py` — 布题（行动区）

**职责**：教师的"行动"出口。像组一份真实的练习卷，而不是"一个题型 × N 道"。

**数据模型（v2，题组制）**：一个任务 = 多个**题组**，每组独立选
知识点 × 题型 × 难度 × 题数，可混合搭配（如 4 道简单单选热身 + 3 道简单填空巩固 +
2 道中等单选提高）。对应后端 `AssignmentItem[]`（`schemas.py`），旧的单题型记录
读取时自动升级。

**放什么**
- 左卡（✏️ 新任务）：标题 → **一键组卷模板** → **题组编辑表**（每行：知识点/题型/
  难度/题数/删除，可增行，上限 8 组）→ 合计条（共 N 道题 · 预计 M 分钟）→ 说明 → 提交；
  - 三个教学法模板：**基础巩固**（简单单选热身 → 简单填空 → 中等收尾）、
    **综合训练**（四种题型中等难度）、**挑战拔高**（困难填空 + 步骤排序为主）；
  - 预计用时按题型基准分钟 × 难度系数估算；
  - **快捷组卷**（表单顶部）：列出最薄弱的 ≤3 个知识点按钮（数据来自 by_topic），
    点击即按该知识点解题率**自动选模板**（<40% 基础巩固 / 40–70% 综合训练 /
    >70% 挑战拔高）生成整份题组并建议标题——这是全页**唯一**的布题入口，
    第二步（诊断区）不放任何布题按钮；
- 右卡（📋 当前任务）：每条任务显示总题数/预计用时/完成情况占位 + 逐题组明细 + 删除；
- 创建成功用 `st.toast` 提示；卡片头注明"学生端尚未接通"（诚实标注 L5）；
- 整个模块包在 `@st.fragment` 里，组卷、增删任务都不触发全页 rerun。

**接口**：`render_assign_panel(ss, topics: list[str], *, create_fn, delete_fn, list_fn) -> None`
提交载荷：`{title, note, items: [{topic, qtype, difficulty, count}]}`

**需要什么数据**

| 字段 | 来源 | 状态 |
|---|---|---|
| 任务 CRUD（items 题组制） | GET/POST/DELETE /assignments | ✅（schema 已升级） |
| `topics` | GET /topics | ✅ |
| 任务完成度/正确率回流 | 待 `answer_submitted` 埋点（事件需带 assignment_id） | ❌ 后端往后放（"完成情况"列显示 "—"） |
| （未来）按班级数据自动选模板 | 该知识点 solve_rate（<40% 用基础巩固、>70% 用挑战拔高） | 可在前端实现，暂用固定"基础巩固" |

### 2.8 `practice_stats.py` — 练习正确率（预留模块）

**职责**：展示**真实做题判分数据**（与 tutor 会话解题率区分开，对应 W3/L5）。

**放什么**
- 每知识点练习正确率 + 答题量的小表/小图；
- 本期后端无数据：渲染空态卡片（"练习判分数据接入后展示"），模块先占位，
  等后端 `answer_submitted` 埋点接通后填充。

**接口**：`render_practice_stats_panel(practice: dict | None) -> None`

**需要什么数据**

| 字段 | 来源 | 状态 |
|---|---|---|
| `practice: {n_answers, correct_rate, by_topic: [{topic, attempts, correct_rate}]}` | GET /analytics/class（待新增） | ❌ 后端往后放 |

### 2.9 编排器 `teacher_app.py`

**职责**：只做四件事——页面配置与主题、拉数据（带缓存）、持有共享状态、把数据和回调分发给各模块。目标：编排器本体 < 100 行。

- 数据拉取：`fetch_class_analytics()` 用 `st.cache_data(ttl=30)` 包裹（D1）；
  侧边栏"刷新数据"改为**先清缓存再 rerun**（修 Q8）；
- 布局：按 §1 的三段结构摆放各 `render_xxx_panel`；
- 状态：见 §3；
- 后端不可达：整页友好报错（沿用现状）。

## 3. 共享状态与模块间交互

### 状态字段（`st.session_state`）

| 字段 | 含义 | 写入方 | 读取方 |
|---|---|---|---|
| `lang` | 界面语言 en/zh | ui.language_toggle | 全部模块（经 i18n.t） |
| `assign_prefill` | 布题预填 `{topic, solve_rate, source}` | assign 内部的快捷组卷按钮 | assign |
| `assistant_history` | 问答对话 `[{role, content}]` | assistant | assistant |
| `include_sim` | 是否纳入模拟数据（演示用） | 侧边栏开关 | 编排器拉数据时传参（后端参数往后放，先只控制徽标文案） |

### 模块间交互

诊断区（第二步）**只读**，不放任何操作按钮；布题动作全部收在第三步内部
（快捷组卷按钮 → `ss.assign_prefill` → 表单自动生成题组 + 来源提示）。
各模块彼此独立，只消费编排器传入的同一份 `/analytics/class` 响应。
